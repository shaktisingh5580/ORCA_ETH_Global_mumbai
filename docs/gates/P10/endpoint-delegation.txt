P10 ENS endpoint delegation

Use two active Sepolia agent names served by distinct ORCA-supported,
factory-verified resolvers. Run the checks from the repository root:

    node arkiv/src/ens.mjs compare-resolvers <target-name> <comparison-name>
    node arkiv/src/ens.mjs endpoint-permissions <target-name> <comparison-name> <delegate-address>

An organization operator can also request POST /v1/identity/ens/endpoint-permissions
with organization_id, ens_chain_id (11155111), first_name, second_name and delegate.
Each request observes one finalized block. A comparison describes the two supplied
names and does not prove no other names point at the resolver.

For an operator to prepare the exact transaction for review:

    node arkiv/src/ens.mjs prepare-endpoint-grant <target-name> <comparison-name> <delegate-address> <controller-address>
    node arkiv/src/ens.mjs prepare-endpoint-update <target-name> <comparison-name> <delegate-address> <https-endpoint>
    node arkiv/src/ens.mjs prepare-endpoint-revoke <target-name> <comparison-name> <delegate-address> <controller-address>

These commands emit an unsigned transaction after simulation on the displayed
finalized block. Recheck current state before signing. A successful simulation is
not a transaction receipt or proof of a live state change. Capture readback after
grant, update and revocation on later finalized blocks. Retain the receipt hashes
and the denied cross-resolver and post-revocation checks for G10 acceptance.

In the workspace, go to Agent onboarding, select an owned service, and
open Resolver permissions under ENSv2 identity. Enter the selected agent's
ENS name, a second agent name and the delegate address, then select Check
permissions. The panel shows the endpoint text role and resolver-wide text
role for each name alongside the finalized block and full observation.

The identity binding signature verifier in arkiv/src/identity-binding.mjs
requires an independently expected manifest. It checks distinct Sepolia and
Rabdi EIP-712 signatures and an Ed25519 service signature. It returns signature
evidence only. The API issues the expected manifest through
POST /v1/identity/agent-bindings/challenges. Supply organization_id, agent_id,
expected_version, name, ens_chain_id and arkiv_wallet. The current active
registration must match the finalized endpoint, card digest and service key
records. The wallet must match the finalized Arkiv wallet text record.

The ENS, Arkiv and service signatures panel issues the same challenge and
downloads its public manifest. To generate the signing payloads in PowerShell:

    Get-Content -Raw <path-to-orca-binding-manifest.json> | node arkiv/src/identity-binding.mjs prepare

Use the ENS and Arkiv typed data with their respective wallets. Sign the
UTF-8 service_statement on the provider host with the service's registered
Ed25519 key. Return the signatures as a JSON object with controller and
wallet as 0x-prefixed hex, and service as unpadded base64url. Paste only
that object in Public signatures JSON and choose Verify signatures. Save
the challenge ID to look up the receipt later as its issuing operator.

Have the controller and wallet sign the manifest with bindingTypedData and the
service sign serviceBindingStatement. Submit organization_id, challenge_id,
controller, wallet and service to POST /v1/identity/agent-bindings. The server
checks the signatures, re-reads finalized ENS state and consumes the challenge
once. GET /v1/identity/agent-bindings/<challenge-id>?organization_id=<org-id>
returns saved evidence to the issuing operator. This workflow uses migration
0043 and starts with the identity:read scope. It does not authorize dispatch.

Live ERC-1271 verification, the institutional credential policy and activation
and revocation of binding authority remain separate acceptance work.
